## The three merge-as-is PRs as a structural set

The three merge-as-is verdicts in this slate are not a random sample. Each represents a structurally distinct "easy yes" archetype:

**block/goose #9028** is a pure docs hardening PR — `ui/goose2/AGENTS.md` only, ~60 net lines, three logical edits: promoting the "frontend → ACP → goose core" architecture diagram from a buried section to right after the build-quickstart block; adding a new section "Don't build features entirely in the frontend" that names 5 specific anti-patterns (business logic in a Zustand store calling `localStorage` / `fetch` / filesystem; `invoke()` proxying to goose instead of an ACP custom method; persisting domain state to `localStorage` with a clarification that it IS appropriate for theme mode / sidebar collapse / last tab; manually duplicating types between TS and Rust instead of using the generated SDK); and updating the feature-organization table to add a "Backend shape" column mapping each pattern (Full-featured / Data-driven / API features / Simple features / Tabs) to its expected backend interaction shape. The verdict-supporting line is the structural framing that "the 'Don't build features entirely in the frontend' section names the failure mode by example, not by abstract principle. The 5 specific anti-patterns map directly to mistakes someone vibing with Cursor / agentic coding tools is most likely to make." That is the right register for an `AGENTS.md` whose audience is part-LLM, and the merge-as-is is justified by codifying an architectural rule the project clearly cares about.

**google-gemini/gemini-cli #26519** is a one-line allowlist extension — adds `'ERR_STREAM_PREMATURE_CLOSE'` to the `RETRYABLE_NETWORK_CODES` array at `packages/core/src/utils/retry.ts:61`, paired with a new 154-line regression test at `packages/core/src/core/issue_25253.test.ts` that wires up a `GeminiChat` instance with a mocked `ContentGenerator` whose `generateContentStream` yields one chunk on the first call, throws an `Error` with `code = "ERR_STREAM_PREMATURE_CLOSE"`, then on the second call yields a second chunk, asserting `callCount === 2`, that a `StreamEventType.RETRY` event was emitted, that two `StreamEventType.CHUNK` events were emitted, and that no `error` event was emitted. The structural justification for the merge-as-is is that `ERR_STREAM_PREMATURE_CLOSE` is the Node `node:stream` synthetic error raised by `finished()` / `pipeline()` when the underlying stream emits `close` before `end` — for the SDK's streaming responses this maps to "the upstream HTTP/2 connection was reset mid-response", which is precisely the class of transient network failure the existing retry-eligible list (`ECONNRESET`, `ETIMEDOUT`, `EAI_AGAIN`, `UND_ERR_HEADERS_TIMEOUT`, `UND_ERR_BODY_TIMEOUT`, `UND_ERR_CONNECT_TIMEOUT`) was built for. The omission was an oversight tied to the SDK's switch from raw fetch to `node:stream`-based readers. The test reproduces the exact issue path (mid-stream throw, not a top-of-call connection failure) and the `(prematureCloseError as any).code = '...'` assignment mirrors how Node actually decorates these errors (a string prop, not a thrown subclass), so the test matches production reality.

**openai/codex #21221** is a pure mechanical refactor — every direct construction of

```rust
JSONRPCErrorError {
    code: INTERNAL_ERROR_CODE,
    message: "...".to_string(),
    data: None,
}
```

is replaced with the existing `error_code::internal_error(...)` helper. Imports of `INTERNAL_ERROR_CODE` are removed wherever the helper now covers the only use. Touches `in_process.rs:553-560, 627-660, 685-700`, `outgoing_message.rs:156-167, 1011-1015, 1137-1141, 1247-1251`, `request_processors.rs:7` (import-only), and `account_processor.rs` in 4 places. One subtle non-mechanical spot: `outgoing_message.rs:156-167` — the previous direct-struct construction inlined `data: Some(serde_json::json!(...))`; the refactor reproduces this via `let mut error = internal_error(...); error.data = Some(...);` — semantics identical, but the `let mut` + post-mutation pattern is the only place in the diff that diverges from the simple `internal_error("msg")` substitution. The verdict justification is structural: this is a semantics-preserving consolidation, no functional change visible to clients, tests migrated alongside, and the `account_processor.rs:354-360` block is even a readability win — the old code used a single struct literal with two ternaries inside `code:` and `message:`; the new `if is_not_found { invalid_request(...) } else { internal_error(...) }` reads top-to-bottom.

These three merge-as-is PRs span three different "easy yes" archetypes — DOCS-HARDENING (goose #9028), ONE-LINE-ALLOWLIST-WITH-REGRESSION-TEST (gemini-cli #26519), and SEMANTICS-PRESERVING-MECHANICAL-REFACTOR (codex #21221). No two of them share a failure mode, so the three merge-as-is verdicts are not redundant evidence of a single trend; they're three independent confirmations that the slate's "easy yes" tail is genuinely structurally varied.

## The five merge-after-nits PRs and the codex #21219 metadata-overlay story as the highest-architectural-leverage catch

The five merge-after-nits verdicts cover opencode #25894 (workspace `/new` fallback fix), opencode #25896 (Windows `cmd.exe /c` MCP shell wrap), codex #21219 (turn-metadata model + reasoning_effort overlay), litellm #27200 (helm `DISABLE_SCHEMA_UPDATE` env var on `migrationJob.enabled`), and qwen-code #3847 (OTel trace_id/span_id injection on debug log files). Each verdict was qualified by a specific concern that doesn't block merge but should land in the same week.

The structurally most-interesting of the five is **openai/codex #21219** — "Add model and reasoning effort to turn metadata", head `a46f9a3`. The PR adds two new keys (`model`, `reasoning_effort`) to the `X-Codex-Turn-Metadata` header that codex emits with every turn-scoped outbound request (model API calls, MCP tool calls, sampling, compact, prewarm). Load-bearing changes:

1. `turn_metadata.rs:22-39` — new `TurnMetadataRequest<'a> { model: &'a str, reasoning_effort: Option<ReasoningEffortConfig> }` struct and a private `TurnMetadataOverlay<'a>` that bundles all four overlay axes (model, reasoning_effort, turn_started_at_unix_ms, responsesapi_client_metadata).
2. `turn_metadata.rs:96-130` — `merge_turn_metadata` rewritten to take an overlay struct instead of two positional args. Crucially, the `responsesapi_client_metadata` filter at `:124-128` now skips reserved keys via a `matches!(key.as_str(), MODEL_KEY | REASONING_EFFORT_KEY | TURN_STARTED_AT_UNIX_MS_KEY)` instead of the previous single `key == TURN_STARTED_AT_UNIX_MS_KEY`. This is the right defensive choice — it prevents user-provided `responsesapi_client_metadata` from clobbering the canonical model/effort.
3. `turn_metadata.rs:248-292` — public API renamed: `current_header_value()` → `current_header_value_for_request(TurnMetadataRequest)`. Internal `build_current_header_value(Option<request>)` is the shared implementation. `current_meta_value()` is deleted; callers now compose `current_header_value_for_request(...)` + `serde_json::from_str` themselves.
4. `turn_context.rs:118-141` — splits the existing `effective_reasoning_effort_for_tracing()` (which returned `String`) into two methods: `effective_reasoning_effort()` returning `Option<ReasoningEffortConfig>` (used by the new metadata path) and the existing tracing wrapper.

The verdict-supporting structural points are that the `TurnMetadataOverlay` struct refactor is pre-emptive — adding the next key (e.g. `personality`, `agent_id`) is now a one-line struct field + one-line merge insert, no more positional-arg explosion — the reserved-key filter widening at `merge_turn_metadata:124-128` is the security-relevant detail and is correctly done (without it, a misconfigured `responsesapi_client_metadata` could spoof the model field), and `effective_reasoning_effort()` returns `None` (not `"default"`) for non-reasoning models so the header overlay only inserts the key when `Some` and non-reasoning model turns won't carry a misleading `reasoning_effort: "default"` string. The merge-after-nits qualifier is to add a `tracing::warn!` on the silent `from_str(&header).ok()` drop at `mcp_tool_call.rs:902`, an explicit `None`-arm test for `reasoning_effort`, and a privacy-disclosure note in the PR body. Functionally the change is clean and the overlay refactor is a real maintainability win.

The other architecturally-interesting catch is **BerriAI/litellm #27200** — "helm: skip proxy startup prisma db push when migrations Job is enabled", head `c9b2481`. The diff scope is `deploy/charts/litellm-helm/templates/deployment.yaml:131-141` (10 inserted lines, 0 removed). When `.Values.migrationJob.enabled` is true, the deployment template now appends `DISABLE_SCHEMA_UPDATE: "true"` to the proxy container's `env:` list. Placement is intentional: the new block sits AFTER both `.Values.envVars` and `.Values.extraEnvVars` rendering, so under Kubernetes' last-wins duplicate-env-name semantics it cannot be silently shadowed by a user-supplied `DISABLE_SCHEMA_UPDATE` in `extraEnvVars`. The accompanying comment at `:134-139` documents that intent inline.

Why this is necessary: when `migrationJob.enabled=true`, schema ownership is supposed to be the dedicated `Job` (which runs once per release with `helm.sh/hook: pre-install,pre-upgrade`). But the proxy `Deployment` was still running `prisma db push` on every pod startup, so on a 5-replica HA rollout you'd get up to 5 concurrent `prisma db push` calls racing against the same Postgres, plus racing the migrations Job itself. Symptoms in the wild are intermittent `prisma migration_lock` advisory-lock contention errors during rollouts. The placement-after-extraEnvVars is the load-bearing detail and is correctly called out in the inline comment — without that ordering rule, a chart user could (intentionally or accidentally) override the safety with a `DISABLE_SCHEMA_UPDATE: "false"` in `extraEnvVars`. The conditional gate on `migrationJob.enabled` is the right toggle key — it inherits the existing chart contract that "enable the Job ⇔ Job owns schema" without introducing a new value. The merge-after-nits qualifier is no `values.yaml` doc update visible in this slice, no `helm unittest` test in `tests/`, and no mention of the `initContainers` migration pattern that some operators use instead of the chart's `Job`.

The remaining three merge-after-nits PRs (opencode #25894 workspace `/new` fallback, opencode #25896 Windows `cmd.exe /c` MCP wrap, qwen-code #3847 OTel trace correlation) are all "right shape, small qualifier" verdicts — opencode #25894 needs a release note for the observable `/new` semantics change and a regression test for the new `defaultWorkspaceID` fallback in `prompt/index.tsx:185`; opencode #25896 needs the Spanish comment at `mcp/index.ts:391` translated to English and (optionally) a one-line note in the commit body explaining the `cmd.exe` vs `pwsh` choice; qwen-code #3847 needs the `prompt_id: promptIdOverride ?? The same is true for the opencode doublet (#25894 + #25896) — #25894 is a workspace-routing fix in the `/new` command path with three logically-distinct changes bundled around the same flow; #25896 is a Windows-specific shell-execution fix for local-MCP `StdioClientTransport` that's completely orthogonal to the workspace path. Both verdicts are merge-after-nits but for entirely independent reasons.
