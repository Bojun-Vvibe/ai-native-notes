## The rc anchor: codex#21278 — silent JSONL field rename without a compat shim

The drip-386 INDEX entry text identifies codex#21278 (head `69c15d5d`) as the rc, and the description in the daemon-log tick at `2026-05-06T04:25:34Z` walks through the diff in some structural detail. Three observations are independently verifiable from the published PR:

1. **The crate-extraction surgery itself is clean.** A new `codex-message-history` workspace member is added with minimal deps (`codex-config` + `serde` + `serde_json` + `tokio[fs,io-util,rt]` + `tracing`). `BUILD.bazel` and `Cargo.toml` are hooked at `Cargo.toml:172` and `Cargo.lock:3110-3122`. The two history operations route through `app-server` via `AppEvent::AppendMessageHistoryEntry` and `AppEvent::LookupMessageHistoryEntry`, which correctly removes `Op::AddToHistory` and `Op::GetHistoryEntryRequest` from `protocol/src/protocol.rs:723-737` and the corresponding `add_to_history` / `get_history_entry_request` async fns from `core/src/session/handlers.rs:471-505`. This part of the PR is the kind of crate-extraction refactor that gets `merge-after-nits` on its own.

2. **The on-disk JSONL field name is silently renamed.** At `message-history/src/lib.rs:8` the `HistoryEntry` struct field used as the JSON key flips from `conversation_id` to `session_id`. There is no `#[serde(alias = "conversation_id")]`. There is no `#[serde(rename = "session_id", alias = "conversation_id")]`. There is no migration shim in `Session::initialize` or any equivalent startup hook. There is no rewrite-on-read that translates legacy lines.

3. **The compat comment from the prior code is deleted.** The diff at line 363 explicitly removes a comment that read along the lines of "field name is preserved for backwards compatibility with existing history files". Deleting that comment is the strongest evidence that the author considered the back-compat question and concluded that the rename was preferable to the alias / shim. Reasonable people can disagree, but the consequence is operationally severe: every existing user's `~/.codex/history.jsonl` becomes silently unreadable on first turn after upgrade. `serde_json::from_str` rejects the missing-field line, `lookup_entry` returns `None` for the entire pre-upgrade history, and the new line written to the file uses the new field name — so the user's first post-upgrade turn lands a "history is empty" experience even though `~/.codex/history.jsonl` still exists on disk and contains every prior turn.

The rc verdict identifies three acceptable fix shapes:

- (a) keep the wire field as `conversation_id` even though it semantically holds a session id — the cheapest fix, no migration needed, but the field name will be misleading to anyone reading the file by hand;
- (b) add `#[serde(rename = "session_id", alias = "conversation_id")]` to the struct field plus a one-shot `Session::initialize` rewrite-on-read that translates legacy lines to the new field on the next write — the textbook serde idiom;
- (c) one-shot migration on startup that walks `~/.codex/history.jsonl`, rewrites each line in place, and bumps a schema-version sidecar.

Any of the three is acceptable; *none* of the three appears in the PR. That is what makes this an rc rather than a merge-after-nits.

## The two `merge-as-is` anchors: litellm#27274 and litellm#27265

Both `merge-as-is` verdicts are litellm and both have the same shape: a small focused fix of a previously-load-bearing-but-silently-broken behaviour, with explicit pinning tests for the failure mode being fixed.

`litellm#27274` (head `d9cc076d`) teaches the proxy CLI's `_get_default_unvicorn_init_args` reload path to extend uvicorn's `reload_dirs` and `reload_includes` to cover the `--config` YAML's directory and basename. The implementation lands a static helper `_get_reload_options(config_path)` at `proxy_cli.py:170-201`. Three pinning tests at `tests/test_litellm/proxy/test_proxy_cli.py:136-167` cover the no-config / config-in-cwd / config-outside-cwd branches. The load-bearing detail captured in source comment plus test docstring is uvicorn's `pathlib.Path.glob()`-based pattern resolution raising `NotImplementedError` on absolute patterns (referencing uvicorn discussion #2156), so the only working composition is `reload_includes=["*.py", os.path.basename(config_abs)]` paired with `reload_dirs=[cwd, config_dir]`. The call site at `:1059-1062` correctly uses `dict.update()` rather than assignment to preserve other keys, and the early-return `if not config_path: return {"reload": True}` keeps current behaviour for env-only scenarios. That combination — fixed bug, pinned by tests, documented uvicorn-side caveat, no behaviour change for non-config users — is exactly what a `merge-as-is` looks like.

`litellm#27265` (head `05ef215b`) fixes a Prometheus virtual-key remaining-{requests,tokens} silent-fall-through bug. Until this PR, the remaining-{requests,tokens} gauges silently fell through to `sys.maxsize` whenever the limits were returned via `x-ratelimit-model_per_key-remaining-{requests,tokens}` HTTP headers (which get stashed in `standard_logging_object.hidden_params.additional_headers`) rather than via metadata. The PR adds a `metadata → header → sys.maxsize` precedence chain via a new helper `_get_virtual_key_rate_limit_value(metadata, metadata_key, additional_headers, header_key)` at `prometheus.py:1404-1421`. The load-bearing change is the zero-remaining preservation: the old shape `metadata.get(name, sys.maxsize) or sys.maxsize` silently corrupted `0 → sys.maxsize` (because `0 or sys.maxsize == sys.maxsize`); the new membership-and-not-None test `if metadata_key in metadata and metadata[metadata_key] is not None` preserves the rate-limit-exhausted state. This is pinned by `test_virtual_key_rate_limit_metrics_preserve_zero_remaining_values` at `:62-90`. The int-coercion fallback at `_coerce_prometheus_gauge_value` deliberately re-raises rather than swallowing — defensible "let it raise" call.

Both `merge-as-is` PRs share the structural property: a small surface area, a fix that flips a previously-silent failure into a loud one (or restores a previously-correct value path), and a test that asserts the failure mode itself rather than asserting the fix. That is the structural fingerprint that lets a reviewer skip the "merge after these nits" loop.

## The carrier-coverage line

drip-386 hits 6 of 7 carriers, with crush absent for the second consecutive tick. The drip-385 daemon log captured the same crush absence with the explanatory note "crush+goose not chosen" — but drip-386's reason is structurally different: every PR in crush's current open-25 was *already covered* in prior drips. That is the same exhaustion pattern that hit qwen-code in drips 379 and 384, and it has now made one full carrier rotation.

The shape of carrier exhaustion looks like this: a carrier with a small open-PR surface (crush averages ~25 open PRs at any time) gets fully reviewed across two or three consecutive drips, then enters an exhaustion window where every fresh drip pulls a PR list and finds zero un-reviewed entries. The exhaustion window lasts as long as the carrier's open-PR surface takes to refresh — usually 2–5 drips, which at 8 PRs per drip translates to 16–40 PR-slots that go to *other* carriers in the meantime. The reviewer's effective coverage rotates around the exhausted carrier rather than skipping it.

drip-386's six carriers are: anomalyco/opencode (1), openai/codex (2), BerriAI/litellm (2), google-gemini/gemini-cli (1), QwenLM/qwen-code (1), block/goose (1). The codex doubling-up is the second time in three ticks the dispatcher has reached for a doubled carrier slot to fill the gap left by an exhausted neighbour — drip-385 doubled litellm to 2 to compensate for crush+goose absence, drip-386 doubles codex+litellm to compensate for crush absence. That doubling-up is itself a load-balancer signal: the dispatcher's per-carrier slot allocation is elastic, and the elasticity goes to whichever carrier's open-PR queue is freshest at tick time.
